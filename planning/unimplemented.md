## 🔴 프로덕션 전 필수

### 1. Apple identity token 서명 검증 미구현
- **파일**: `backend/src/main/java/com/cloumy/auth/oauth/AppleOAuthClient.java`
- **현재 상태**: identity token(JWT)의 서명을 검증하지 않고 Base64 payload만 디코딩해서 사용
- **위험**: 위조된 identity token으로 타인 계정 탈취 가능
- **해야 할 것**: Apple 공개키 JWK endpoint(`https://appleid.apple.com/auth/keys`)에서 공개키를 가져와 RS256 서명 검증 추가
- **참고**: JJWT 또는 `com.nimbusds:nimbus-jose-jwt` 라이브러리 사용 권장

### 2. JWT 블랙리스트 조회가 Redis 장애 시 처리되지 않은 예외를 던짐
- **파일**: `backend/src/main/java/com/cloumy/auth/security/JwtTokenProvider.java` (validateToken, `redisTemplate.hasKey(BLACKLIST_KEY_PREFIX + ...)` 부분)
- **관련 태스크**: Rate Limiting 튜닝(Spring, 2026-07-04) 검증 중 발견 — `RateLimitFilter`의 fail-open 동작을 확인하려고 Redis 컨테이너를 잠깐 내렸더니, 내 필터에 도달하기도 전에 `JwtAuthenticationFilter`가 블랙리스트 조회에서 `RedisException`을 던져 500으로 응답함(정상 토큰인데도)
- **위험**: Redis 장애 시 인증이 필요한 모든 엔드포인트가 500을 반환 — 정상 사용자도 전부 막힘. 레이트리밋은 fail-open으로 설계했는데 그 앞단인 인증 자체가 fail-closed(사실상 의도치 않은 예외)라 전체 취지가 무색해짐
- **해야 할 것(논의 필요)**: 블랙리스트 조회를 try-catch로 감싸고 Redis 장애 시 정책 결정 필요 — "차단된 토큰인지 확인 불가 시 통과시킬지(로그아웃 처리가 늦게 반영되는 정도의 리스크)" vs "명시적으로 503 반환할지"(현재처럼 이유 불명확한 500보다는 나음)
- **우선순위**: 중간 — Redis 자체가 자주 죽는 컴포넌트는 아니지만, 장애 시 파급 범위가 이 기능 하나가 아니라 전체 인증이라 영향도가 큼

## 🟠 테스트 미완료

### 2. JWT 인증 흐름 엔드-투-엔드 테스트 미완료
- **관련 태스크**: JWT 인증 미들웨어 구현
- **현재 상태**: 코드 구현은 완료, 실제 서버 구동 후 테스트 미진행
- **테스트해야 할 흐름**:
  1. `POST /v1/auth/social` → Access/Refresh Token 발급 확인
  2. 발급된 Access Token으로 보호된 API 호출 → 200 확인
  3. 만료된 Access Token 사용 → 401 `TOKEN_EXPIRED` 확인
  4. `POST /v1/auth/refresh` → 새 Access Token 발급 확인
  5. `POST /v1/auth/logout` → Redis 블랙리스트 등록 확인
  6. 로그아웃된 Refresh Token으로 갱신 시도 → 401 `TOKEN_REVOKED` 확인

- **우선순위**: 중간 — 지금 당장 뭔가 깨지진 않지만(폴백이 있어서), 유저가 고른 테마가 실제로는 절반 이상 무의미하게 무시되고 있다는 건 핵심 기능(AI 루트 생성 + 예산 자동조정 + 페르소나 자동추가)의 체감 품질에 영향을 줌

## 🔵 탐색 탭 장소 정보 보강 (사진 + 한줄 요약 — 2026-07-10)

### (번호추가) 탐색 탭 장소에 사진 + 한줄 요약 추가 예정
- **관련 태스크**: 탐색 탭(장소 브라우징+북마크) 구현 후 논의. 장소마다 사진을 나중에 추가할 예정인데, 그와 짝을 이룰 "이 장소가 어떤 곳인지" 한줄 요약도 필요하다고 판단
- **현재 상태**: 후보로 검토했던 두 방법 모두 지금 당장 쓸 데이터가 없음을 확인
  - **AI 루트 tip 재사용은 부적합**: `route_slots.tips`는 장소 자체 속성이 아니라 특정 루트/일정 문맥에서 AI가 생성한 코멘트라 같은 장소도 루트마다 다른 tip을 가질 수 있음. 실제 DB 확인 결과 tip이 있는 슬롯 42건 중 서로 다른 장소는 31개뿐(전체 21,545개 중), 그마저 일부는 장소당 tip이 2개씩 달라 "이 장소의" 한줄로 쓸 정답이 없음
  - **사용자 리뷰 요약은 방향은 맞지만 콜드스타트**: 장소 자체에 대한 일반적 정보라 성격은 더 맞지만, 리뷰 작성 UI·저장 구조·AI 요약 파이프라인이 전부 없고 리뷰 데이터도 0건이라 지금 당장 구현해도 보여줄 게 없음
- **해야 할 것(논의된 방향)**: 두 소스를 섞는 하이브리드로 결정
  1. TourAPI 출처 장소(`places.source = 'tourapi'`)는 `detailCommon2`(현재 미사용 — 수집 스크립트가 `areaBasedList2` 목록 API만 호출해 소개문 필드 자체를 안 받아옴, `ai/scripts/collect_tourapi.py`)에 이미 관광공사가 작성한 소개문이 있어 이걸 한줄로 다듬어 사용(품질 제일 좋음, 단 추가 API 호출 필요 — 21,545건 개별 상세 조회라 배치 규모 있음)
  2. 소개문이 없는 출처(카카오/히든젬)는 이름+주소+category_tags 기반으로 AI가 짧게 생성 — `translate_places.py`/`PlaceService.getPlaceDetail`의 실시간 캐시 패턴(배치로 기존 건 일괄 채우고, 신규 장소는 첫 조회 시 실시간 생성+캐시)을 그대로 재사용 가능
- **다음 순서**: 사진 추가 작업과 묶어서 "장소 정보 보강" 하나의 기능으로 나중에 정식 브레인스토밍 예정(사용자 지정)
- **우선순위**: 낮음 — 사진 기능 착수 시점에 함께 진행
