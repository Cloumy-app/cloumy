# 프로액티브 개입 엔진 — 챗봇을 "먼저 말 거는" 구조로 전환하는 설계

> 상태: **검토 중(미승인)** · 작성 2026-07-27
> 아직 확정 전이다. 개입 규칙(§5)과 열린 질문(§10)은 특히 추가·수정 여지가 크다.

## 배경

노션 「0. 방향성 v4」(2026-07-24)와 「1. 문제 정의」(2026-07-24)가 챗봇의 성격을 재정의했다.

**v3 → v4 변경 핵심:** "여행 중 실행"의 성격을 **리액티브(물으면 답)** 에서 **프로액티브(놓치기 전에 먼저 챙김)** 로 재정의하고, 그 챙김을 커뮤니티가 쌓는 운영현실 데이터로 증명하는 것을 정체성으로 삼는다.

이 전환의 배경은 2026-07-24 딥리서치다. TripGenie(Trip.com)가 in-trip 프로액티브를 이미 하고 있다는 사실이 확인되면서, **챗봇은 해자가 아니라 웨지(강점·얼굴)** 로 강등됐고 해자는 "취향 검증 커뮤니티 → 운영현실 데이터 플라이휠"로 옮겨갔다. 「1. 문제 정의」는 이를 더 명시적으로 적었다:

> **MVP 기둥 ② 챗봇 = 프로액티브 개입 엔진**
> 단 챗봇 혼자가 아니라 **루트(앵커)·커뮤니티 데이터(연료)** 가 받쳐야 성립한다 — GPT가 못 하는 이유가 정확히 그 둘의 부재다.

즉 노션 스스로 **"엔진만으로는 성립 안 된다"** 를 인정하고 있다. 이 설계는 그 전제 위에서 **엔진을 먼저, 연료는 다음 프로젝트로** 분리한다.

### 현재 챗봇 구현 (2026-07-06 완료 시점 기준)

`docs/06-ai-chatbot.md`가 as-built 문서다. 요약하면:

| 항목 | 현재 |
|---|---|
| 진입 | `POST /ai/chat` — 유저가 보낼 때만 동작하는 단발 요청·응답 |
| 도구 | 3종 읽기전용 — `search_nearby_places` / `get_weather_forecast` / `get_route_status` |
| 모델 | Haiku 기본, `_SONNET_KEYWORDS` 또는 히스토리 10턴 초과 시 Sonnet |
| 세션 | Redis `chat:{user_id}:{route_id}`, TTL 7200s, 최대 40메시지 |
| 위치 | GPS 없이 `_estimate_current_slot()` — `routes.start_date` + `route_slots.start_time` vs 현재 KST |
| 출력 | 자연어 답변 + 장소 카드 + `insertion_anchor`(카드 탭 → 루트 삽입) |
| UI | `frontend/app/(tabs)/chat.tsx` — 입력창 + 말풍선. **먼저 말 거는 표면 없음** |
| 보호 | Spring 이중 소유권 검증 + `RateLimitFilter` `/v1/chat` 분당 10회 |

구현 중 발견된 정합성 문제 3가지:

1. **시스템 프롬프트가 아직 "트리피(Tripy)"** — `ai/app/services/chat_service.py:66`. 앱명이 Cloumy로 바뀐 뒤 갱신 안 됨
2. **`places.business_hours` / `places.trend_score` 는 선언만 돼 있고 비어 있음** — 값을 넣는 코드가 저장소에 없다(`Place.java`는 매핑에서 제외했고, 프로젝트에 스케줄러 자체가 하나도 없다). 따라서 영업시간·트렌드 기반 개입은 **불가능**하다. 라스트오더를 영업 종료 시각으로 근사하는 것도 안 된다
3. **챗봇이 Trip Pass 유료 기능인데 게이팅이 없음** — `PassValidationService`는 이미 있으나 `ChatController`가 호출하지 않음

## 범위

**포함:**
- 프로액티브 개입 엔진 — 트리거 **①앱 열 때만**
- 개입 규칙 — **여행 전 브리핑 1종 + 여행 중 7종** (§5)
- `routes.departure_at` 컬럼 신설 + 출국 일시 입력 UI (T7 전제)
- 루트 화면 배너 노출 → 탭 → 챗봇으로 맥락 전달
- 배너 노출·탭·닫음 이벤트 로깅 (§7)
- 프로액티브 엔드포인트 레이트리밋 + 날씨 예보 Redis 캐시 (§6)
- 기존 챗봇 최소 정합성 수정 — 트리피→Cloumy

**제외:**
- **운영현실 데이터**(라스트오더·휴무·웨이팅·off-corridor) — 스키마 신설 + 수동 시딩 200곳이 필요한 별도 프로젝트. 이게 없으면 프로액티브의 진짜 가치가 안 나오지만, 엔진과 데이터는 독립적으로 만들 수 있다
- **트리거 ②예약된 시각 푸시 알림** — Expo Push 토큰 관리 + 서버 스케줄러 + 권한 플로우가 통째로 필요. `planning/milestones.md:315`의 "핫플이 됐어요 FCM 알림"과 함께 묶어서 다루는 게 낫다
- **트리거 ③대화 중 능동 개입** — 분량이 크고 ①을 먼저 검증한 뒤가 맞다
- **Trip Pass 게이팅** — `PassValidationService.validate()` 한 줄이면 되지만 결제 PG가 미구현이라 지금 켜면 전원이 막힌다. 결제 트랙과 함께
- **기존 도구 3종 재설계** — 예산 도구(`get_budget_status`) 추가 등은 별도. 예산 기능이 이제 구현됐으므로 가능해지긴 했다(2026-07-05 당시엔 미구현이라 제외했던 항목)

## 결정 배경 (2026-07-27 논의)

목적을 **베타 실사용**으로 잡았다. 사업계획서 데모용이 아니라 베타 테스터 50명이 실제 여행 중 쓸 수 있는 수준을 목표로 한다.

**데이터를 범위 밖으로 뺀 이유.** 운영현실 데이터는 수동 시딩부터 시작해야 하고(노션 Phase 0 콜드스타트: 서울 K-culture 핵심 200곳), 입력 도구·검수 흐름까지 딸려온다. 엔진과 같이 하면 둘 다 어중간해진다. 대신 **엔진을 데이터가 늘어나도 안 부서지는 모양으로** 만든다(§4).

**트리거를 "앱 열 때"만으로 좁힌 이유.** 푸시는 인프라가 통째로 필요한데, 프로액티브가 실제로 먹히는지도 아직 모른다. 앱 열 때만으로 먼저 재보고, 탭률이 나오면 그때 푸시로 확장한다.

**배너를 루트 화면에 둔 이유.** 챗봇 탭 안에 두면 챗봇 탭을 안 여는 유저에겐 안 보인다 — 노션 KPI "챗봇 사용률 40%"(피벗 기준 20% 미만)를 그대로 남기는 셈이다. 여행 중 가장 자주 보는 루트 화면에 띄우고 챗봇으로 유도한다.

## 핵심 설계 결정

### 판단은 규칙이, 표현은 앱이

접근안 3가지를 놓고 비교했다.

| | 판단 주체 | 지연 | 추적 | 비용 |
|---|---|---|---|---|
| **A. 규칙 엔진 + i18n 템플릿** ⭐ | 규칙 | 없음 | 가능 | 0 |
| B. Spring에 규칙 엔진 | 규칙 | 없음 | 가능 | 0 |
| C. LLM이 개입 여부까지 판단 | LLM | 1~2초 | 불가 | 호출당 |

**A를 택했다.**

C를 버린 결정적 이유는 지연이나 비용이 아니라 **재료 부족**이다. 지금 가진 신호는 날씨·시각·이동시간·예산 정도인데, 이걸 LLM에 주고 "먼저 챙겨봐"를 시키면 뻔한 것을 그럴듯하게 포장한 말을 만들어낸다. 노션 「0. 방향성」이 경계한 *"데이터 없는 알림은 GPT도 하는 잔소리"* 가 정확히 이것이다. **재료가 적을수록 규칙이 정직하다.**

B는 데이터 소유(routes·slots·expenses가 Spring 것)라는 장점이 있지만 두 가지가 걸린다. **날씨가 Spring에 없다** — 프론트가 OpenWeatherMap을 직접 호출하고(`frontend/lib/api/weather.ts`), 서버 쪽은 `ai/app/services/weather_service.py`에만 있다. 그리고 `_estimate_current_slot()`을 Java로 재구현해야 해서 같은 로직이 두 벌이 된다.

**서버는 상태 코드만 반환하고 문구는 앱이 만든다.** 응답에 한국어가 한 글자도 없으므로 4개 언어가 기존 i18n으로 자동 해결된다.

### AI를 나중에 얹을 수 있는 모양으로

데이터가 늘면 후보가 동시에 여러 개 뜨기 시작하고, 그때는 "뭘 먼저 말할지" 고르는 일이 규칙으로 버겁다. 그 시점에 **고르는 함수만** 교체할 수 있게 짠다.

```
❌ 조건 체크 → 바로 배너 하나 반환          (AI 낄 자리 없음)
✅ 조건 체크 → 후보 목록 → 그중 1개 선택 → 반환
                              ↑
                    지금은 priority 정렬
                    나중엔 이 함수만 LLM으로 교체
```

규칙층은 데이터가 아무리 늘어도 남는다 — AI가 규칙을 대체하는 게 아니라 규칙이 뽑은 후보 위에 얹힌다. 교체 시점은 "데이터가 많아졌을 때"가 아니라 **"후보가 동시에 여러 개 뜨기 시작했을 때"** 다.

### 확신이 낮으면 아예 안 띄운다

`route_slots.start_time`은 **계획일 뿐** 실제 진행 상황이 아니다. 체크인·방문 인증이 없으므로 유저가 늦잠을 자도 시스템은 계획대로 진행 중이라고 본다.

- `_estimate_current_slot()`의 `confidence != "high"` 면 **위치에 의존하는 규칙(T2·T6·T7)을 건너뛴다**. T1·T3·T4·T5는 위치와 무관해서 계속 평가한다
- 문구를 단정형으로 쓰지 않는다 — "지금 경복궁이시죠?"(❌) / "다음 일정까지 30분 걸려요"(⭕)

## 개입 규칙 (초안 — 확정 전)

### 설계 원칙 — 계획과 현실의 어긋남을 어떻게 우회하는가

`route_slots.start_time`은 계획일 뿐이고 실제 진행 상황은 알 수 없다(§확신이 낮으면 안 띄운다). 이건 방어일 뿐 해결이 아니다 — 유저가 조금만 늦어져도 모든 개입이 침묵한다. 규칙을 이 약점을 우회하는 세 축으로 나눈다.

```
① 어긋나기 전에 개입한다        → 여행 전 (P1)
② 어긋나도 상관없는 개입을 한다  → 계획 정확도가 필요 없는 것 (T1·T3·T4·T5)
```

세 번째 축으로 "어긋난 걸 유저에게 되물어 보정한다"(`LONG_ABSENCE`)도 검토했으나 제외했다 — 아래 §검토했으나 뺀 것 참조.

**개입이 가장 값진 순간은 여행 중이 아니라 여행 전날이다.** 개입의 가치는 정확도가 아니라 "유저가 아직 뭘 할 수 있느냐"에 비례하는데, 여행 중엔 숙소도 표도 동선도 이미 정해져 있다. 전날이면 일정을 통째로 갈아엎을 수 있고, 짐 싸기에도 영향을 준다. 노션이 "여행 중 실행"을 강조하다 보니 초안에서 이 축을 놓쳤다.

### 여행 전 (D-1)

**P1. `PRE_TRIP_BRIEFING`** — 여행 시작 전날 앱을 열면 뜬다. 개별 규칙이 아니라 **여러 진단을 한 배너에 묶어** 전달한다.

| 진단 항목 | 조건 |
|---|---|
| 날씨 | Day별 강수확률 ≥ 0.6 → "우산 챙기세요" |
| 폭염·한파 | Day별 최고 ≥ 33℃ 또는 최저 ≤ -5℃ |
| 빡빡한 Day | 슬롯 ≥ 5개 **AND** 총 이동시간 ≥ 180분 |
| 숙소에서 먼 밤 일정 | 그 날 마지막 슬롯 → 숙소 이동시간 ≥ 40분 |
| 긴 도보 구간 | `transport_to_next = 'walk'` **AND** `transport_minutes ≥ 40` |
| 첫 일정 시각 | 항상 표시 ("첫 일정은 9시 경복궁") |

`params: { nights, destination, flags: [...] }` — 해당하는 진단만 배열로 담고, 앱이 i18n으로 조립한다.

초안의 `OVERPACKED`(빡빡한 Day)와 별도로 제안됐던 "숙소에서 먼 밤 일정"·"걸어서 40분"이 전부 여기로 흡수됐다. **전부 여행 중엔 이미 늦은 진단들**이라 D-1이 올바른 타이밍이다.

### 여행 중

우선순위는 숫자가 낮을수록 먼저. 여러 후보가 동시에 뜨면 최우선 1개만 반환한다. **`confidence != "high"` 면 T2·T6·T7을 건너뛴다**(현재 슬롯 추정에 의존하므로). T1·T3·T4·T5는 위치와 무관해서 항상 평가한다 — 계획이 어긋나도 살아남는 규칙들이다.

| # | 코드 | 조건 | params | 우선 | 노션 |
|---|---|---|---|---|---|
| T1 | `FLIGHT_DEPARTURE` | `departure_at − 공항이동(근사) − 체크인 2h − now` 가 0~60분 | `departureAt`, `leaveByTime` | 1 | ⑥ |
| T2 | `DEPARTURE_SOON` | 다음 슬롯 `start_time − transport_minutes − now` 가 0~15분 | `nextPlaceName`, `minutesLeft`, `transportMinutes` | 2 | ① |
| T3 | `EMPTY_DAY` | 오늘 Day의 슬롯이 0~1개 (오전 중에만) | `day`, `slotCount` | 3 | — |
| T4 | `WEATHER_ALERT` | 강수확률 ≥ 0.6 **또는** 최고 ≥ 33℃ / 최저 ≤ -5℃, **AND** 그 Day에 `#실내` 없는 슬롯 1개 이상 | `day`, `kind`(rain\|heat\|cold), `outdoorCount` | 4 | ② |
| T5 | `BUDGET_OVER` | 오늘 지출 합 > `total_budget / (nights+1)` × 1.2 | `spentToday`, `dailyBudget` | 5 | ⑦ |
| T6 | `BOOKMARK_NEARBY` | 추정 슬롯 반경 500m 내 유저 북마크 장소 중 오늘 루트에 없는 것 | `placeName`, `distanceM` | 6 | ⑪ |
| T7 | `FREE_GAP` | 현재 슬롯 종료 후 다음 슬롯까지 공백이 이동시간 + 60분 이상 | `gapMinutes` | 7 | ⑤ |

**T1(출국)이 최우선인 이유:** 다른 규칙은 놓쳐도 "못 갔네" 정도지만 비행기는 놓치면 재앙이다. 실패 비용이 압도적으로 크다. 그리고 인천공항까지 얼마나 걸리는지, 언제 나가야 하는지는 방한 외국인이 감을 못 잡는 대표적인 "현지인의 암묵지"다. 공항 이동시간은 정확할 필요가 없어 도시별 상수(예: 서울→인천 90분) 근사로 충분하다 — 여유를 두는 게 목적이다.

**T3(오늘 일정 비었음)이 값진 이유:** "일정이 없다"는 추정이 아니라 **사실**이라 계획 정확도가 전혀 필요 없다. 그리고 마지막 날은 대부분 비어 있는데(짤 때 "출국이니까" 하고 대충 둔다), 막상 가보면 비행기까지 반나절이 남아 **"오늘 뭐하지"가 여행 전체에서 가장 절실한 질문**이 된다. T1과 짝을 이룬다.

### 검토했으나 뺀 것 — `LONG_ABSENCE` (보정 규칙)

"여행 중인데 마지막 앱 실행이 48시간 이상 전이면 '일정이 계획대로 가고 있나요?'라고 되묻는다"를 검토했다. 우리는 계획이 어긋났는지 알 방법이 없지만 **오랜만에 열었다는 사실 자체가 약한 신호**이고(잘 쓰고 있으면 매일 연다), 유저 답을 받으면 그 세션 동안 위치를 보정해 다른 규칙도 정확해진다는 발상이었다. 노션 시나리오 ③(일정 밀림)을 체크인 없이 우회하는 방법이기도 했다.

**2026-07-27 논의에서 제외하기로 했다.** 잘못 쓰면 "왜 안 들어왔냐"는 잔소리로 읽히고, 다른 규칙이 유저에게 뭔가를 주는 반면 이것만 유저에게 뭔가를 요구해서 성격이 다르다. 계획-현실 갭 보정은 나중에 체크인·GPS 인증(Hidden Gems 연계)이 생길 때 제대로 다루는 게 맞다.

- `#실내` 태그 — `places.category_tags`. `ai/app/services/route_service.py:59`가 루트 생성 시 이미 쓰고 있다. `#실내`가 없으면 실외로 간주하는 게 현재 방식

### 노션 시나리오 15개 중 못 하는 것

| 시나리오 | 막힌 이유 |
|---|---|
| ⑫ 라스트오더 · ⑬ 언어 되는 곳 · ⑭ 예약 벽 · ⑧ 혼잡도 | **운영현실 데이터가 본체** — 지금 넣으면 빈 규칙이 된다 |
| ④ 공연 후 야식·귀가 | 콘서트·이벤트 앵커 기능이 미구현(노션 📋) |
| ⑨ 교통 지연 | 실시간 교통 API 미연동(현재는 좌표 기반 근사) |
| ③ 일정 밀림 | 체크인·GPS 인증이 없다. 되묻기로 우회하는 안을 검토했으나 제외(§검토했으나 뺀 것) |
| ⑩ 컨디션 | **구조적으로 불가능** — 물어봐야 아는데 물으면 프로액티브가 아니다 |

즉 우리가 지금 만드는 규칙은 대체로 "다른 앱도 할 수 있는 층"(날씨·시간·예산은 공개 데이터)이고, **진짜 차별점이 되는 것들은 정확히 데이터가 없어서 못 만든다.** 예외는 T6(북마크 근처)뿐 — "이 사람이 뭘 저장했는지 + 지금 어디쯤인지"를 둘 다 알아야 해서 데이터 없이도 우리만 할 수 있다. 베타에서 T6 탭률이 높게 나오면 개인화된 개입이 먹힌다는 신호이고, T2·T4만 탭되고 T6가 죽으면 프로액티브의 가치가 생각보다 얕다는 뜻이다.

## 아키텍처 & API 계약

```
[앱] 루트 화면 진입
  ↓ GET /v1/routes/{routeId}/proactive
[Spring] ProactiveController
  · 소유권 검증 (ChatController와 동일 패턴)
  · AiServiceClient로 프록시
  ↓ GET /ai/proactive?user_id=&route_id=
[FastAPI] proactive_service
  ① 스냅샷 수집 (route + slots + estimated_slot + weather + budget + bookmarks)
  ② 규칙 평가 (P1 / T1~T7) → 후보 목록
  ③ 후보 중 1개 선택 (지금은 priority 정렬)
  ↓
{ "type": "WEATHER_RAIN", "params": { "day": 2, "outdoorCount": 3 } }  또는 null
  ↓
[앱] 배너 렌더 — 문구는 locales/*.json 에서 조회
```

**배너 탭 시 챗봇 맥락 전달:**

```
[루트 화면] 배너 탭
  → 챗봇 탭으로 이동
  → useChatStore 에 assistant 메시지 1개 삽입 (배너와 동일 문구)
  → pendingProactiveContext 저장
  → 유저가 답장하면 그 첫 메시지에만 컨텍스트를 실어 전송
  → chat_service 가 시스템 프롬프트에 "[방금 먼저 안내한 내용]" 으로 덧붙임
  → 전송 후 컨텍스트 클리어
```

맥락을 안 넘기면 챗봇이 "응 바꿔줘"만 받고 뭘 바꾸란 건지 모른다.

**중복 노출 방지:** `{routeId}:{type}:{날짜}` 키로 MMKV에 기록해 그날은 다시 안 띄운다. 서버에 기록할 만한 가치가 아직 없어 로컬로 둔다.

## 성능 · 비용 방어

프로액티브는 **앱을 켤 때마다** 호출되므로 `/v1/chat`(유저가 의도적으로 보낼 때만)과 성격이 다르다.

**① 레이트리밋.** `RateLimitFilter`의 `RULES`에 항목 추가. 기존 두 개(`/v1/routes/generate` 3회/분, `/v1/chat` 10회/분)와 같은 패턴. 한도는 앱 재진입을 감안해 넉넉히 잡되(예: 30회/분) 무한 루프는 막는다.

**② 날씨 캐시가 필수다.** `_get_forecast_by_block()`은 httpx로 OpenWeatherMap을 직접 호출하고 **캐시가 없다.** 프로액티브가 앱 열 때마다 이걸 부르면 유저 몇 명만 붙어도 무료 티어 한도가 터진다. `{도시}:{날짜}` 키로 Redis 캐시(TTL 1~3시간)를 넣는다. 챗봇의 `get_weather_forecast` 도구도 같은 캐시를 타게 되어 덤으로 이득이다.

**③ LLM 호출 없음.** 규칙 평가는 DB 조회 + 캐시된 날씨뿐이라 응답이 즉시 나온다. `planning/milestones.md:399`의 "챗봇 2초 이내" 기준과 무관하게 배너는 훨씬 빠르다.

## 계측 — 이게 없으면 베타의 의미가 없다

노션 「9. 로드맵 & KPI」에 **"상황 맞춤 정보 열람율 ≥ 60%"** 가 있는데, 이벤트 로깅 설계에는 프로액티브 관련 이벤트가 **하나도 없다.** 지금 설계대로 만들면 잴 방법이 없다.

베타의 목적이 "프로액티브가 먹히는가"를 확인하는 것이므로, 안 재면 돌려도 배운 게 없다. 최소 3개:

```
proactive_shown      { type }                 어떤 종류가 떴나
proactive_tapped     { type }                 탭해서 챗봇까지 갔나   ← 핵심 지표
proactive_dismissed  { type }                 그냥 닫았나
```

**종류별 탭률**을 보면 어떤 개입이 쓸모 있는지 바로 나온다. 쓸모없는 규칙은 베타 중에 뺀다. 규칙을 여러 개 한 번에 넣는 게 부담스럽지 않은 이유도 이것이다 — 측정해서 솎아낼 수 있다. 특히 개인화 가설의 시금석인 T6를 주시한다.
