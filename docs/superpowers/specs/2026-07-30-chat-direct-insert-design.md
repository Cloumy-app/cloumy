# 대화로 자리를 명시했으면 확인 없이 바로 추가 — 설계

- **날짜**: 2026-07-30
- **선행 작업**: 챗봇 추천 장소를 루트에 추가 (2026-07-29, 미커밋)
- **범위**: `ai/` + `frontend/` (Spring은 주석만)

---

## 1. 배경

「챗봇 추천 장소를 루트에 추가」(2026-07-29)는 삽입 자리를 **①대화 맥락 → ②위치 추정 → ③오늘 Day 맨 뒤** 3단으로 정하고, 그 결과를 **항상 확인 시트로 보여준 뒤** 사용자가 확정하게 했다. 당시 "맥락 있으면 원탭 / 없으면 피커"라는 두 갈래를 하나로 합친 의도적 단순화였다.

실사용 검토에서 사용자가 지적한 것:

> "어디 가기 전에 카페나 들리고 싶다 할 때는 그냥 바로 루트에 추가하는 건 어때. 이건 언제 갈지를 명시적으로 설명해주는 거잖아"

맞는 지적이다. 「경복궁 가기 전에 카페」라고 말한 사용자에게 *"경복궁 앞에 넣을까요?"* 라고 되묻는 건 방금 한 말을 되풀어 확인받는 것이다. 자리가 이미 하나로 정해진 경우에 시트는 마찰이다.

### 그런데 `source: "conversation"`을 그대로 쓸 수 없다

`chat_service._resolve_from_conversation`은 **신뢰도가 다른 두 경로**에서 같은 값을 낸다:

| 사용자 발화 | 서버가 정한 자리 | 지금 `source` |
|---|---|---|
| "**경복궁 가기 전에** 카페" | 경복궁 슬롯을 찾아 그 앞 — **자리가 하나로 확정** | `conversation` |
| "**2일차에** 카페" (또는 장소명 매칭 실패) | 2일차 **맨 뒤** — 사용자가 "맨 뒤"라고 말한 적 없다 | `conversation` |

두 번째는 서버가 임의로 고른 자리다. `source === "conversation"`이면 바로 넣도록 만들면 **사용자가 지정하지 않은 위치로 조용히 삽입**된다.

### 같은 혼동이 이미 오문구를 만들고 있다

day-only 케이스도 `afterSlotId`가 그 Day 마지막 슬롯으로 채워지므로, `InsertPlaceSheet`의 분기 조건(`source === 'conversation' && anchorSlotName`)에 걸린다. 그 결과 시트가 **"말씀하신 대로 〈그 Day 마지막 장소〉 다음에 추가할까요?"** 라고 말한다 — 사용자는 그 장소를 말한 적이 없다. **기존 버그이고, 신호를 쪼개면 함께 고쳐진다.**

### 의도한 결과

- 「경복궁 가기 전에 카페」 → 카드 탭 → **시트 없이 바로 추가**
- 「2일차에 카페」 → 카드 탭 → **기존대로 시트로 확인** (맨 뒤는 사용자가 말한 자리가 아니다)
- 탭 **전에** 어디로 갈지 보여줘서 잘못된 매칭을 누르기 전에 알아챌 수 있게 한다

## 2. 서버 — `source`를 신뢰도로 쪼갠다

`_resolve_from_conversation`의 두 반환 경로를 분리한다.

| 경로 | 지금 | 바뀐 후 |
|---|---|---|
| 장소명 매칭 성공 → 그 슬롯 앞/뒤 | `conversation` | `conversation` *(유지)* |
| 장소 매칭 실패 or 장소 없이 Day만 → 그 Day 맨 뒤 | `conversation` | **`conversation_day`** |

**기존 값을 강한 쪽에 남기는 이유**: 앱의 `conversationAfter` i18n 문구("말씀하신 대로 …")가 이제 **실제로 장소를 말한 경우에만** 걸리게 되어 오문구가 저절로 고쳐진다. 반대로 배정하면 문구 분기를 따로 손봐야 한다.

`conversation_day`는 앱의 어느 분기에도 안 걸려 `defaultEnd`("2일차 마지막에 추가할까요?")로 떨어진다 — **그게 사실이므로 새 i18n 키가 필요 없다.**

**Spring**: `ChatInsertion`은 `String source`라 코드 변경이 없다. 주석의 값 목록만 갱신한다.
**프론트**: `ChatInsertion.source` 유니온에 `'conversation_day'`를 더한다.

## 3. 앱 — 카드 탭 분기

`frontend/app/(tabs)/chat.tsx`의 `PlaceCardList`:

```
handlePress(place)
  ├─ insertion?.source === 'conversation'  → 바로 insertRouteSlot(afterSlotId, day)
  └─ 그 외                                  → setSheetPlace(place)  (기존)
```

바로 추가 경로는 시트의 `handleConfirmInsert`와 **같은 삽입 로직**을 쓴다(`insertRouteSlot` → `invalidateQueries(['route-slots'])` → `addedIds` 추가). 로직을 복제하지 않고 공용 함수로 뽑아 두 경로가 공유한다 — 삽입 성공/실패 처리가 갈라지면 한쪽만 고치는 사고가 난다.

### 404면 시트로 폴백

기준 슬롯이 다른 기기에서 이미 삭제된 경우(기존 FFE #6)다. 바로 추가 경로에서 이걸 조용히 실패시키면 사용자는 왜 안 됐는지 모른다. 기존 404 분기를 그대로 재사용해 **알림 → 슬롯 목록 무효화 → `forceManualPick`으로 시트 열기**로 처리한다. 즉 "바로 추가는 낙관적 경로이고, 깨지면 확인 경로로 내려간다."

## 4. 앱 — 탭 전 예고

`chat.insertHint`("탭하면 다음 일정 사이에 추가돼요") 자리를 조건부로 바꾼다.

| 상태 | 문구 (ko) |
|---|---|
| `conversation` + 앵커 슬롯 이름 있음 | 「Day 1 · 광화문」 다음에 바로 추가돼요 |
| `conversation` + `afterSlotId === null` | 「Day 1」 맨 앞에 바로 추가돼요 |
| 그 외 | *(기존 문구 그대로)* |

**Day를 함께 보여주는 이유**: `_match_slot`은 부분 일치를 쓰고 같은 이름이 여러 Day에 있으면 "오늘 이후 첫 번째"를 고른다. 드물지만 의도와 다른 Day가 잡힐 수 있고, Day를 명시하면 누르기 전에 눈에 띈다.

**앵커(앞 장소) 기준으로 쓰는 이유**: 서버는 `afterSlotId`(= 「경복궁」의 **앞** 슬롯)만 내려준다. 사용자가 말한 「경복궁」을 그대로 되뇌려면 `targetSlotId` 필드를 AI→Spring→프론트 3계층에 추가해야 하는데, 「광화문 다음」과 「경복궁 앞」은 **같은 자리**이므로 필드를 늘릴 값이 없다.

슬롯 이름은 `useQuery(['route-slots', routeId])`로 가져온다 — `InsertPlaceSheet`가 이미 쓰는 **같은 캐시 키**라 새 API 호출이 없다.

i18n 4개 언어(`ko`/`en`/`ja`/`zh`)에 키 2개 추가.

## 5. FFE — 실패 시나리오

| # | 상황 | 대응 |
|---|---|---|
| 1 | 슬롯 캐시가 아직 안 옴 | 예고는 기존 문구로 폴백. **탭은 그대로 바로 추가** — 자리는 서버가 이미 정했으니 이름 없이도 유효하다 |
| 2 | 바로 추가 중 404 (기준 슬롯 삭제됨) | 알림 → 슬롯 목록 무효화 → 시트 열고 `forceManualPick` |

| 4 | 같은 장소 두 번 탭 | 기존 `addedIds` / `insertingId` 가드 그대로 |
| 5 | `insertion` 자체가 없음 (구버전 서버) | 시트 경로 — 카드가 죽지 않는다(2026-07-29 FFE #11 유지) |

| 7 | `conversation`인데 `afterSlotId`가 이 루트에 없는 id | Spring이 404 → #2와 같은 경로 |

## 8. 구현 후 실기기 검증에서 나온 수정 (2026-07-30)

시뮬레이터로 「고척 스카이돔 가기 전에 카페에 들르고싶어」를 실제로 쳐보니 **되묻고 카드도 안 떴다.** 두 가지가 겹쳐 있었다.

### 8-1. `origin="place"` 지시 범위가 좁았다 (설계 결함)

프롬프트와 도구 설명에 **「경복궁 근처」, 「남산공원 주변」** 같은 *근접* 표현만 적었다. 그런데 이 기능의 출발점인 **「X 가기 전에 카페」** 는 *삽입 위치* 표현이다. 모델은 이걸 검색 기준점 신호로 읽지 않아 → "지금 어디 계신지" 되묻거나 → 엉뚱한 기준점(추정 슬롯)을 썼다. 오타 없이 세션을 비워도 재현됐으므로 오타 탓이 아니다.

**고친 방법 — 모델에게 두 인자를 요구하지 않고 서버가 유도한다.** `_origin_place_hint(tool_input)`가 `origin_place` → `insert_before_place` → `insert_after_place` 순으로 장소명을 찾는다. "X 가기 전에 카페"는 **검색 기준점과 삽입 자리가 같은 장소**를 가리키는 한 문장이니 신호는 하나로 받는 게 맞다. 프롬프트도 *"사용자가 특정 장소를 입에 올렸다면 어떤 표현이든 … 절대 되묻지 마세요"* 로 넓혔다.

검증: 검색 중심이 `126.8669, 37.4992`로 나왔고 이건 **고척 스카이돔 좌표와 정확히 일치**한다. `places` 5건, `source=conversation`, 앵커 = 한강레져스포츠.

### 8-2. Spring 15초 타임아웃 (사용자 승인 후 처리)

`AiServiceClient.java:211`이 15초인데 챗봇 한 요청의 LLM 왕복이 **3회**(메인 2회 + `_generate_place_reasons` Haiku 1회)여서 4~15초로 흔들렸다. 타임아웃 시 `chat()`이 예외를 던져 **카드가 아예 안 뜬다.**

`_generate_place_reasons`를 제거하고 `describe_candidate`(LLM 없음)로 되돌렸다 — 왕복 3회 → 2회. **3.9~5.5초로 안정화**(Spring 경유 end-to-end 9.3초).

이건 2026-07-06에 사용자 피드백으로 도입한 것을 되돌린 것이라 `planning/unimplemented.md`에 "문구가 다시 단조로워짐"을 별건으로 기록했다. 거리순 정렬 자체는 오히려 쿼리를 **30배 빠르게** 했다(849ms → 28ms, `ORDER BY RANDOM()`이 느렸다).

### 8-3. 함께 발견한 별건 결함

모델이 같은 세션에서 두 번째 장소 질문에 **도구를 안 부르고 히스토리의 장소를 읊는다** → `places: None` → 카드 없음. 규칙 1 위반이고 이번 수정과 별개다. `unimplemented.md`에 기록.

## 9. 범위 밖 (기존 결정 유지)

| 항목 | 왜 빼는가 |
|---|---|
| 되돌리기(undo) | 탭 전 예고로 실수 자체를 줄이는 쪽을 택했다. 잘못 들어가면 루트 화면에서 삭제한다 |
| `targetSlotId` 신설 | 「광화문 다음」과 「경복궁 앞」은 같은 자리다 — 3계층에 필드를 늘릴 값이 없다 |
| 「어느 장소 뒤」 세밀 선택 | Day 단위로 먼저 내고 실사용을 본다 |
| 카드에 거리 배지 | 별건 (근처 검색 정확도 작업의 범위 밖 항목) |
